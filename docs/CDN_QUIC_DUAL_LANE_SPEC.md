# Архитектурная спецификация: Протокол CDN-QUIC & Dual-Lane (v2)
**Проект:** `lordik-server` (`tproxy-server`)  
**Статус:** Архитектурный стандарт / Техническое задание для AI-агентов разработки  
**Целевое назначение:** Устранение межпотоковой блокировки очереди (Head-of-Line Blocking), обеспечение мгновенного отклика интерфейса Telegram при параллельной загрузке тяжелых медиафайлов через CDN и сокращение задержек рукопожатия до уровня нативных VLESS XHTTP / MTProto-WS решений.

---

## 1. Контекст и решаемая проблема

В транспорте первого поколения (`cdn`, `cdn-ws` v1) все логические потоки Telegram (`stream_id: 1..N`) мультиплексируются в единый байтовый конвейер с глобальной последовательной нумерацией:
* **На Uplink:** используется единый счетчик пакетов `upSeq = 1, 2, 3...` и общий `ReassemblyBuffer` на всю сессию.
* **На Downlink:** используется один HTTP-стрим с единым курсором `downCursor` и общей FIFO-очередью `pendingFrames`.

### Почему это ухудшает пользовательский опыт (UX) через CDN:
1. **Межпотоковый Head-of-Line (HoL) Blocking на Uplink:** Если клиент отправляет фото или видео в потоке `stream_id = 5` и один из HTTP-запросов (`upSeq = 14`) задерживается на пограничном узле CDN или попадает на TCP-ретрай, сервер блокирует обработку `upSeq = 15`, в котором находится текстовое сообщение или запрос открытия чата из потока `stream_id = 1`.
2. **Монополизация Downlink тяжелым медиа-трафиком:** Когда сервер отдает крупные блоки видео (по 256–512 КиБ) в единственный открытый `ReadableStream`, управляющие кадры (`WINDOW`, `OPEN`, `CLOSE`) и мелкие обновления текстовых чатов вынуждены ждать в конце очереди.
3. **Задержка холодного старта TCP к дата-центрам Telegram (`direct.go`):** На каждый новый кадр `OPEN` сервер выполняет синхронный `net.DialTimeout` к IP-адресу дата-центра Telegram, теряя 30–100 мс на TCP Handshake перед отправкой первых 64 байт `Obfuscated2`.
4. **Троттлинг JS-моста мобильной ОС:** Однопоточный цикл обработки в WebView замораживается планировщиком Android/iOS при сворачивании или скроллинге, если не удерживаются системные блокировки активности.

## 2. Общая архитектурная схема (v2)

Архитектура v2 базируется на **четырех независимых механизмах**, работающих поверх стандартного HTTP/2 и HTTP/3 (QUIC) соединения с CDN без изменения контракта с нативным клиентом Telegram:

```text

│                            КЛИЕНТ (Telegram App + WebView)                             │
│                                                                                        │
│  Telegram Core <══> SharedFrames [type:1B][stream_id:3B][len:4B][payload]              │
│                           │                                                            │
│                           ▼                                                            │
│              ┌─────────────────────────┐                                               │
│              │  Smart QoS Classifier   │ (Разделение по типу кадра и объему потока)    │
│              └─────┬─────────────┬─────┘                                               │
│                    │             │                                                     │
│   [VIP: Control/UI]│             │ [Bulk: Media/Files]                                 │

│    CLOSE, < 4 КиБ) │             │  или параллельные медиа-коннекты)                   │

│  │  Stream #1 (Чат/API): [s_seq: 1, 2, 3] ──► (Не ждет Stream #4!) ──► Сокет DC2    │  │
│  │  Stream #4 (Видео):   [s_seq: 1, _, 3] ──► (Ждет только свой #2) ──► Сокет DC-2  │  │
```

## 3. Детальная спецификация узлов архитектуры

### 3.1. Неизменность контракта с клиентом Telegram (Инвариант)
1. Взаимодействие между WebView и приложением Telegram (`window.TelegramWebProxy`, инициализация `#android=<nonce>`, `MessagePort` `tproxy-init`) остается **строго неизменным**.
2. В метод `port.postMessage()` кадры `SharedFrame` передаются строго по одному, с валидным 8-байтовым заголовком:
   ```text
   +---------------+-------------------+-----------------------+-------------------+
   | Type (1 byte) | StreamID (3B BE)  | PayloadLen (4B BE)    | Payload (N bytes) |
   +---------------+-------------------+-----------------------+-------------------+
   ```
3. Все изменения протокола v2 инкапсулируются исключительно на участке **«JS-мост в шаблоне $\leftrightarrow$ Go-сервер `lordik-server`»**.

---

### 3.2. Узел 1: Per-Stream Framing и независимая сборка на Uplink (QUIC-style)

Вместо нарезки общего обезличенного буфера на чанки с единым счетчиком `upSeq`, вводится **по-потоковая фрагментация и нумерация (`StreamSubFrame`)**.

#### Формат Uplink-пакета (Sub-Frame Envelope):
При поступлении кадра `SharedFrame` от Telegram в `queueCarrier(buf)`, JS-мост читает его `type` (1B) и `stream_id` (3B BE). Если кадр превышает максимальный размер чанка (`maxChunkBytes`, например, 6000 байт), мост разбивает его на самодостаточные суб-кадры конкретного `stream_id`.

Каждый суб-кадр внутри HTTP-запроса (GET или POST) имеет заголовок **9 байт (Big-Endian)**:
```text
+---------------+-------------------+--------------------+--------------------+-----------------+
| Type (1 byte) | StreamID (3B BE)  | StreamSeq (2B BE)  | SubFlags (1 byte)  | SubLen (2B BE)  |
+---------------+-------------------+--------------------+--------------------+-----------------+
|                                   Sub-Payload (SubLen bytes)                                  |
+-----------------------------------------------------------------------------------------------+
```
* **`Type` (uint8):** Тип исходного кадра (`0x01` OPEN, `0x02` DATA, `0x03` CLOSE, `0x04` WINDOW).
* **`StreamID` (uint24 BE):** Идентификатор логического потока Telegram (`0` для сессионных кадров, `1..N` для потоков).
* **`StreamSeq` (uint16 BE):** Монотонно растущий порядковый номер суб-кадра **внутри данного `StreamID`** (начинается с `1` при открытии потока, переходит через `65535 -> 0`).
* **`SubFlags` (uint8):**
  * Бит `0x01` (`FLAG_FIRST`): Начало нового исходного `SharedFrame`. Если установлен, первые 4 байта `Sub-Payload` содержат `TotalFrameLen (uint32 BE)` исходного кадра, либо сервер собирает кадр до флага `FLAG_FIN`.
  * Бит `0x02` (`FLAG_FIN`): Последний фрагмент текущего `SharedFrame` (для мелких кадров $\le 6\text{ КиБ}$ установлены оба бита `0x01 | 0x02 = 0x03`).
* **`SubLen` (uint16 BE):** Длина полезной нагрузки данного фрагмента в байтах.

*(Допускается упаковка нескольких мелких суб-кадров разных потоков в один HTTP-запрос при коалесценции).*

#### Логика на сервере (`internal/session/`):
1. Глобальный `ReassemblyBuffer` сессии заменяется (или дополняется для v2) индивидуальным `streamReassembly` внутри каждого `logicalStream` (и отдельным буфером для `stream_id == 0`).
2. Когда на сервер приходит HTTP-запрос с одним или несколькими суб-кадрами:
   * Сервер читает `StreamID` и `StreamSeq`.
   * Суб-кадр помещается в `stream.reassembly` конкретного потока.
   * Если `StreamSeq == stream.expectedSeq`, данные **немедленно** собираются и отправляются в TCP-сокет бэкенда этого потока (`direct` / `telemt` / `mtproxy`), **не дожидаясь** пропущенных пакетов в других потоках!

### 3.3. Узел 2: Двухуровневый планировщик QoS (Dual-Lane: VIP + Bulk)

Чтобы тяжелые видеопотоки не вызывали задержку открытия чатов и отправки сообщений, вводится классификация трафика на стороне сервера и клиента.

#### Правила классификации потока:
1. **VIP-трафик (Interactive Priority):**
   * Все управляющие кадры: `OPEN (0x01)`, `CLOSE (0x03)`, `WINDOW (0x04)`.
   * Кадры `DATA (0x02)` любого потока, у которого суммарный объем переданных данных (`bytesSent + bytesRecv`) с момента открытия еще не превысил **64 КиБ** (фаза рукопожатия MTProto, RPC-запросы, загрузка текста сообщений).
   * Кадры `DATA (0x02)` размером менее **4096 байт** в потоках, где нет активной очереди крупных сегментов.
2. **Bulk-трафик (Media / File Transfer):**
   * Кадры `DATA (0x02)` потоков, прокачавших более **64 КиБ** и передающих сегменты размером $\ge 8\text{ КиБ}$.

#### Реализация на сервере (`internal/session/session.go`):
* Вместо одного среза `pendingFrames [][]byte` сессия хранит две очереди:
  * `vipFrames [][]byte` (высокий приоритет)
  * `bulkFrames [][]byte` (фоновый медиа-трафик)
* При формировании батча на отправку клиенту (`takeDownBatchLimitLocked(maxBytes)`):
  1. Сначала в батч целиком выбираются все кадры из `vipFrames`.
  2. Оставшееся место в батче заполняется из `bulkFrames`, но **размер одного батча в режиме стриминга принудительно ограничивается 64–128 КиБ** (вместо 512 КиБ).
  3. Благодаря нарезке по 64–128 КиБ время записи одного конверта в сокет составляет $< 1\text{ мс}$, и любой новый `VIP`-кадр вклинивается между кусками видео мгновенно.

#### Реализация на клиенте (JS-мост):
* **Immediate First Dispatch (0 мс задержки):** Если `upInflight === 0`, любой поступивший от Telegram кадр отправляется в сеть **синхронно в том же тике (`flushUplink()`)** без ожидания `setTimeout(..., 2)`. Таймер коалесценции (2 мс) включается только для последующих кадров, пока первые уже летят в сети.
* **Приоритетная очередь Uplink:** На клиенте `upQueue` разделяется на `vipQueue` и `bulkQueue`. Свободные слоты `upInflight` всегда сначала забирают пакеты из `vipQueue`.

### 3.4. Узел 3: Multi-Stream Downlink + Reorder Buffer + Fast Retransmit (NACK)

Одиночный HTTP/2-стрим через CDN часто ограничивается алгоритмом TCP Congestion Control пограничного узла или шейпингом на один поток.

#### Архитектура параллельного стриминга (2–3 воркера):
1. Клиент может держать открытыми **от 1 до 3 параллельных GET-стримов** (`GET /assets/media/{short_id}/stream_{cursor}_{lane}_{rand}.m4s`).
   * **Lane 0 (Базовый стрим):** открывается сразу при старте сессии.
   * **Lane 1..2 (Ускорители медиа):** автоматически подключаются при обнаружении плотного потока данных (например, когда скорость приема превышает 128 КиБ/с или приходят полные батчи подряд) и закрываются при простое.
2. Сервер выдает каждому активному стриму следующий атомарный батч с монотонно растущим `Next DownCursor (uint32 BE)` в 8-байтовом заголовке конверта (`StreamEnvelope`):
   ```text
   +------------------------------------+------------------------------------+
   | Next DownCursor (uint32 BE, 4 B)   | Batch ByteLength (uint32 BE, 4 B)  |
   +------------------------------------+------------------------------------+
   |                 Payload: Raw SharedFrames (N bytes...)                  |
   +-------------------------------------------------------------------------+
   ```
3. **Клиентский буфер переупорядочивания (`DownlinkReorderBuffer`):**
   * Так как `Batch #11` в `Lane 1` может прийти на 10 мс раньше, чем крупный `Batch #10` в `Lane 0`, клиент проверяет условие: `batch.prevCursor === expectedDownCursor`.
   * Если батч пришел по порядку — он немедленно передается в `deliver(payload)`, а `expectedDownCursor` сдвигается вперед; после чего из `reorderMap` достаются все следующие за ним готовые батчи.
   * Если батч пришел раньше времени (`batch.prevCursor > expectedDownCursor`) — он сохраняется в `reorderMap` (лимит до 16 батчей).
4. **Механизм Fast Retransmit (NACK):**
   * Если в `reorderMap` появился батч с курсором впереди ожидаемого, клиент запускает таймер `250 мс`.
   * Если через `250 мс` пропущенный батч `expectedDownCursor` так и не пришел (завис один из параллельных стримов), клиент отправляет легковесный запрос повторной выдачи (`?ack={expectedDownCursor}&nack=1`) и перезапускает зависший стрим-воркер. Сервер при получении `nack=1` немедленно отдает неподтвержденный батч из `unackedBatches` в ответ на этот запрос!

### 3.5. Узел 4: Прогретый пул сокетов к Telegram DC (`WarmDCPool` в `direct.go`)

Для режима `backend_type: "direct"` устраняется задержка на установку TCP-соединения к серверам Telegram при открытии каждого нового потока.

#### Алгоритм работы пула:
1. В `internal/session/direct.go` создается глобальный (или привязанный к менеджеру) потокобезопасный пул `WarmDCPool`.
2. Для основных дата-центров Telegram (`DC 2`, `DC 4` и медиа-кластеров `DC -2`, `DC -4`) фоновый воркер поддерживает по **2 готовых TCP-соединения** (`net.Conn` с включенным `SetNoDelay(true)` и `SetKeepAlive(true)`).
3. **Короткий TTL жизни в пуле:** Соединение в пуле считается свежим не более **15 секунд**. По истечении 15 секунд неиспользованный сокет закрывается и заменяется новым, чтобы избежать выдачи полузакрытых (half-open) сокетов со стороны балансировщиков Telegram.
4. **Безопасная выдача с Fallback-ретраем:**
   * Когда клиент присылает первые 64 байта рукопожатия `Obfuscated2`, сервер извлекает `dcID`, берет готовый сокет из `WarmDCPool` за `0 мс` и сразу записывает в него трансформированный 64-байтовый заголовок + первый пакет данных (`firstData`).
   * Фоновая горутина тут же пополняет пул новым соединением.
   * **Защита от протухшего сокета:** Если запись первых байт в сокет из пула вернула ошибку, сервер **не закрывает поток клиента**, а прозрачно выполняет штатный `net.DialTimeout` на новый сокет и записывает сохраненный `firstData` туда.

### 3.6. Узел 5: Анти-троттлинг среды исполнения WebView

Для предотвращения засыпания JS Event Loop на смартфонах:
1. **Удержание `Web Locks API`:** При активации сессии скрипт моста запрашивает бесконечный лок:
   ```javascript
   if (navigator && navigator.locks && navigator.locks.request) {
     navigator.locks.request('tproxy_active_session', { mode: 'shared' }, () => new Promise(() => {}));
   }
   ```
   В движках Chromium / Android WebView наличие активного `Web Lock` сигнализирует планировщику не замораживать таймеры вкладки в фоне.
2. **Опциональный вынос сетевого цикла в `Web Worker` (с автоматическим откатом):**
   * Поскольку некоторые профили `Hardened WebView` могут блокировать создание `Blob Worker` через CSP, инициализация воркера обязана быть обернута в `try/catch` с проверкой работоспособности за 50 мс. При запрете код бесшовно исполняется в основном потоке.

## 4. Технические требования к реализации

### 4.1. Требования обратной совместимости (`.omp/RULES.md`)
1. Все существующие режимы (`https`, `https-lanes`, `websocket`, `websocket-lanes`, `cdn-adaptive`, `cdn-get`, `cdn-body`, `cdn-ws`, `yc-ws`) должны продолжать работать без регрессий.
2. Новая логика должна либо активироваться через версионирование при рукопожатии (`v: 2` в `init` запросе моста / новый профиль `cdn-quic`), либо расширять `cdn-ws` обратно-совместимым флагом возможностей, чтобы старые сессии не ломались.
3. Полное сохранение **Active Probing Resistance**: любой неавторизованный запрос, неверный токен сессии или несовпадение `VHost` (`profile.EffectiveHostname`) на новых или измененных эндпоинтах обязаны возвращать ответ сайта-прикрытия (`vhost.servePublic(w, r)`), не выдавая заголовков прокси.

### 4.2. Требования к памяти и безопасности (Memory & Resource Budgets)
1. **Лимит памяти на `streamReassembly`:**
   * Окно внеочередных суб-кадров на один логический поток: не более `32` слотов (`maxStreamWindowSpan = 32`).
   * Максимальный суммарный объем буферизованных внеочередных фрагментов на один поток: `256 КиБ`.
   * Максимальный суммарный объем всех `streamReassembly` буферов в рамках одной сессии: строго ограничен `limits.MaxSessionBufferBytes`.
2. **Корректный учет `pendingCost` и `unackedBytes`:**
   * Переход на две очереди (`vipFrames` и `bulkFrames`) должен сохранять точный подсчет байтов в `s.pendingBytes`. При закрытии сессии (`Close()`) обе очереди и все `streamReassembly` буферы должны очищаться без утечек памяти.
3. **Потокобезопасность (`go test -race`):**
   * Выдача батчей нескольким параллельным горутинам `StreamCDN` (Lane 0..2) и ответы на `nack=1` должны синхронизироваться через мьютекс сессии `s.mu` без гонок данных и без дублирования одного и того же курсора двум разным стримам.

## 5. Анализ потенциальных проблем и способы их решения (Risk Mitigation)

Разработчики и AI-агенты **обязаны** учесть следующие 6 краевых случаев при написании кода:

### Проблема 1: Гонка между кадром `OPEN` и первым кадром `DATA` в разных HTTP-запросах
* **Сценарий:** Клиент отправляет `OPEN (stream_id = 3, s_seq = 1)` в первом HTTP-запросе и следом `DATA (stream_id = 3, s_seq = 2)` во втором параллельном HTTP-запросе. Из-за джиттера CDN запрос с `DATA (s_seq = 2)` приходит на сервер на 5 мс раньше, чем запрос с `OPEN (s_seq = 1)`.
* **Что произойдет при наивной реализации:** Сервер увидит `DATA` для еще не существующего в таблице `s.streams[3]` потока и отклонит пакет с ошибкой протокола!
* **Нормативное решение:**
  Если на сервер приходит суб-кадр с `StreamID > 0` и `StreamSeq > 1`, а потока `s.streams[StreamID]` еще нет (и он не числится в `closedStreams`), сервер **не возвращает ошибку**, а создает «ожидающий инициализации» слот `pendingStream` с `streamReassembly` (с начальным `expectedSeq = 1`) и кладет туда `s_seq = 2`. Как только через 5 мс долетает `OPEN (s_seq = 1)`, сервер выполняет `openStream`, затем тут же проигрывает `s_seq = 2`!

### Проблема 2: Зависание одного из параллельных стримов Downlink (`ReorderBuffer` Stall)
* **Сценарий:** Открыты 2 параллельных стрима скачивания (`Lane 0` и `Lane 1`). Сервер отдал `Batch #50` в `Lane 0`, а `Batch #51` — в `Lane 1`. Соединение `Lane 0` «замерзло» на промежуточном маршрутизаторе CDN без закрытия TCP-сокета, а `Lane 1` продолжает присылать `Batch #51, #52, #53...`.
* **Что произойдет при наивной реализации:** Клиент будет бесконечно ждать `Batch #50`, буфер переупорядочивания `reorderMap` переполнится, и сессия зависнет.
* **Нормативное решение:**
  1. На сервере: не выдавать новые батчи, если разница между самым старым неподтвержденным батчем в `unackedBatches` и текущим курсором превысила лимит окна (`maxUnackedBatches = 16`).
  2. На клиенте: при появлении «дырки» в `reorderMap` запускать таймер **Fast Retransmit (250 мс)**. По срабатыванию таймера:
     * Отправить запрос досылки конкретного пропущенного батча (`sendRetransmitReq(expectedDownCursor)`).
     * Принудительно вызвать `abort()` на том стрим-воркере (`Lane`), который дольше всех не присылал данные.

### Проблема 3: Голодание (`Starvation`) Bulk-потоков или переполнение памяти VIP-очередью
* **Сценарий:** Если отдавать абсолютный 100% приоритет `vipFrames`, то при аномальном шторме мелких кадров медиа-поток может полностью остановиться.
* **Нормативное решение:**
  Использовать **Weighted Deficit Round-Robin (квотирование внутри батча)**:
  * В каждом цикле `takeDownBatchLimitLocked(128 KiB)` под `vipFrames` выделяется до `32 КиБ` гарантированной полосы в начале батча, а оставшиеся до `96 КиБ` заполняются из `bulkFrames` (если `bulkFrames` пуста — `vipFrames` может занять все `128 КиБ`). Это гарантирует мгновенный проход всех управляющих кадров и сообщений, сохраняя стабильную скорость прокачки видео.

### Проблема 4: Закрытие потока (`CLOSE`) при наличии несобранных фрагментов в `streamReassembly`
* **Сценарий:** Пользователь отменил загрузку большого файла в Telegram. Клиент отправляет кадр `CLOSE (stream_id = 5, s_seq = 40)`, в то время как фрагменты `s_seq = 38, 39` еще летят через CDN или потерялись.
* **Нормативное решение:**
  * На сервере: при закрытии потока по инициативе бэкенда или по таймауту `streamId` заносится в кольцевой буфер `recentlyClosedStreams` (например, последние 64 закрытых `stream_id`). Любые запоздавшие суб-кадры для уже закрытого `stream_id` молча отбрасываются (`200 OK` без ошибки сессии).
  * Если от клиента приходит `CLOSE (0x03)` с `s_seq > expectedSeq`, он ставится в очередь `streamReassembly` по своему `s_seq`, чтобы штатно закрыть поток после досылки последних байт, либо (после таймаута 2 сек) принудительно закрывает поток и очищает буфер.

### Проблема 5: Выдача «мертвого» TCP-сокета из `WarmDCPool` в `direct.go`
* **Сценарий:** Балансировщик Telegram закрыл простаивающее TCP-соединение через 12 секунд (`FIN`/`RST`), а сервер взял его из пула на 13-й секунде.
* **Нормативное решение:**
  1. Перед выдачей сокета из пула выполнять неблокирующую проверку живости (установка `SetReadDeadline` в прошлое или `syscall.Recvfrom(..., MSG_PEEK | MSG_DONTWAIT)` на Linux).
  2. Обернуть отправку первого пакета (`firstData`) в `connectAndRelay` в блок с прозрачным фолбэком: если `Write(firstData)` в сокет из пула вернул ошибку, немедленно выполнить прямой `net.DialTimeout` и повторить `Write(firstData)` на свежем соединении.

### Проблема 6: Буферизация мелких конвертов на прокси-сервере (Nginx / Caddy)
* **Сценарий:** Если `lordik-server` стоит за локальным Nginx/Caddy, прокси может пытаться буферизовать ответ `model/gltf-binary`, не отдавая 64-килобайтные конверты клиенту сразу.
* **Нормативное решение:**
  В каждом потоковом ответе `serveCDNStreamDown` в обязательном порядке выставлять заголовки:
  * `X-Accel-Buffering: no` (отключает буферизацию в Nginx)
  * `Cache-Control: no-store, no-transform` (запрещает модификацию и сжатие на CDN)
  * Вызывать `flusher.Flush()` строго после каждого записанного конверта `StreamEnvelope`.

## 6. Дорожная карта поэтапного внедрения (Для AI-агентов)

Чтобы минимизировать риски и тестировать изменения изолированно, разработка разбивается на **3 последовательных этапа (Milestones)**:

### Этап 1 (Milestone 1): QoS Dual-Lane Планировщик + `WarmDCPool` на сервере
* *Изменения только на Go-сервере (обратно совместимо с текущим JS-мостом!):*
  1. Разделить `pendingFrames` в `internal/session/session.go` на `vipFrames` и `bulkFrames` с классификацией по типу кадра (`OPEN`, `WINDOW`, `CLOSE`) и объему потока ($< 64\text{ КиБ}$).
  2. Уменьшить максимальный размер одного конверта в режиме стриминга (`StreamCDN`) до `128 КиБ`, чтобы VIP-кадры проскакивали между чанками видео с задержкой $< 5\text{ мс}$.
  3. Реализовать `WarmDCPool` в `internal/session/direct.go` с TTL 15 секунд и прозрачным фолбэком на `net.DialTimeout`.
  4. Покрыть unit-тестами приоритезацию очередей и выдачу сокетов из пула.

### Этап 2 (Milestone 2): Per-Stream Uplink Framing (Устранение HoL-блокировки отправки)
* *Изменения в `internal/session/cdn.go`, `internal/server/cdn.go` и шаблоне моста:*
  1. Реализовать структуру `PerStreamReassembly` на сервере (с поддержкой создания буфера для потока до прихода `OPEN` при переупорядочивании запросов на CDN и игнорированием пакетов для `recentlyClosedStreams`).
  2. Обновить упаковщик Uplink в JS-мосте для формирования 9-байтовых заголовков `StreamSubFrame` (`[type][stream_id][stream_seq][flags][len]`) и разделения очередей отправки на `vipQueue` и `bulkQueue`.
  3. Написать тесты на независимую доставку: задержка фрагмента в `stream_id = 4` не должна задерживать доставку кадра в `stream_id = 1`.

### Этап 3 (Milestone 3): Multi-Stream Downlink + ReorderBuffer + Fast Retransmit (NACK)
* *Изменения в `internal/server/cdn_stream.go`, `internal/session/session.go` и шаблоне моста:*
  1. Разрешить подключение до 2–3 параллельных читателей `StreamCDN` на одну сессию (конкурентные воркеры `Lane 0..2` без взаимного вытеснения `superseded`).
  2. Добавить поддержку параметра `?nack=1&ack={cursor}` для мгновенной повторной выдачи потерянного батча из `unackedBatches`.
  3. Внедрить на клиенте `DownlinkReorderBuffer` и таймер Fast Retransmit (250 мс).
  4. Провести нагрузочное тестирование с `go test -v -race ./...`.
